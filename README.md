# tg-business-kit

One Telegram bot engine for small service businesses — language schools, dental clinics, beauty studios, tutors. Every client is one JSON profile: services, weekly slots, FAQ and UI texts. The engine turns it into a button-driven booking flow, an FAQ menu and AI answers grounded strictly in the profile; whatever the profile does not answer goes to the owner.

Status: phase 3 of 4 — long polling and a webhook server, Postgres with migrations, an owner API, Docker, CI. Without `DATABASE_URL` the bot falls back to an in-memory store for quick demos.

## Try it

```bash
uv sync
uv run python -m kit validate presets/*.json
uv run pytest                     # Postgres half skipped without a database

docker compose --profile test up -d testdb
TEST_DATABASE_URL=postgresql://kit:kit@127.0.0.1:5434/kit_test uv run pytest   # both halves
```

Every test that touches storage runs twice, on the in-memory store and on Postgres, against the same contract.

Run a bot against your own test token (create one with @BotFather):

```bash
uv run python scripts/setup_env.py          # hidden prompts, writes .env (600)
uv run python -m kit run --profile presets/dental-clinic.json
```

## Docker

```bash
uv run python scripts/setup_env.py --generated-only   # POSTGRES_PASSWORD, ADMIN_API_TOKEN
docker compose up -d --build                     # Postgres, migrations, long-polling bot
docker compose --profile webhook up -d --build   # + webhook server on 127.0.0.1:8000
```

`migrate` is a one-shot service: the bot starts only after it exits 0. Migrations are plain SQL in `migrations/`, applied in order under an advisory lock (`python -m kit migrate`).

`KIT_PROFILE=presets/language-school.json` picks another business. The webhook port is bound to localhost on purpose: put a TLS reverse proxy in front of it, then `uv run python scripts/set_webhook.py https://<host>/telegram/webhook`.

Check a running webhook server without Telegram:

```bash
uv run python scripts/synthetic_update.py http://localhost:8000/telegram/webhook "hi"
uv run python scripts/synthetic_update.py http://localhost:8000/telegram/webhook --no-secret   # 403
uv run python scripts/webhook_info.py
uv run python scripts/api_leads.py http://localhost:8000     # GET /api/leads with ADMIN_API_TOKEN
```

The owner API is described at `/api/docs`. It answers 404 until `ADMIN_API_TOKEN` is set.

## Design notes

- **One booking per business at a time.** `save_lead` takes a transaction-scoped advisory lock on the business, then checks slot capacity and the per-client limit, then inserts. A small business books a few times an hour, so the queue costs nothing, and the code stays obviously correct.
- **Telegram retries are expected.** The webhook records `(bot, update_id)` with `insert ... on conflict do nothing` before handling an update, so a re-delivery is handled once, across restarts and instances.
- **Serverless later needs a pooler.** Each instance opens a small pool; on a serverless platform put a transaction-mode pooler between the functions and Postgres.

## Environment

| key | needed for |
|---|---|
| `TELEGRAM_BOT_TOKEN` | always |
| `GEMINI_API_KEY` | `modules.ai_answers` |
| `ADMIN_USER_ID` | owner notifications and `/leads` |
| `WEBHOOK_SECRET` | `serve` — generated by `scripts/setup_env.py` |
| `DATABASE_URL` | Postgres; set by compose, unset = in-memory store |
| `POSTGRES_PASSWORD` | the compose database — generated |
| `ADMIN_API_TOKEN` | `GET /api/leads` — generated; unset = endpoint off |
